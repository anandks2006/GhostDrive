1. Executive Summary
GhostDrive is a desktop application that turns free-tier accounts and local storage into a unified, encrypted, redundant personal cloud drive. Supported backends: Telegram, Discord, Local Folder, NAS/SMB, and External Drive. No dedicated server required. No backend ever sees plaintext data.
Primary use cases: large machine-learning artifacts (model checkpoints, datasets) alongside irreplaceable personal files (family photos, documents). Two redundancy categories match engineering effort to actual importance. A headless CLI companion and browser UI share the same service layer and database.

2. Problem Statement
- Google Drive 15 GB free tier fills rapidly with ML checkpoints and training datasets.
- Paid storage is a recurring cost compounding over time.
- Existing tools (Telegram-Drive, YouTubeDrive, D-Drive) use single backends, no encryption, no redundancy.
- No existing tool treats client-side encryption as a first-class requirement.
- No tool offers tiered redundancy matched to file criticality.

4. Cryptographic Architecture
4.1 Algorithm Stack
Algorithm
Role
Rationale
Argon2id
Passphrase ? keystore key
Memory-hard, GPU-resistant. Auto-calibrated to ~1 s. Runs ONCE per session at unlock. Never re-derived mid-session.
HKDF-SHA512
Master Key ? subkeys
Defined salt (random 32-byte, generated at first run, stored in keystore.json). Defined info strings per key purpose. Different info = cryptographically isolated subkeys.
ChaCha20-Poly1305
Chunk payload streaming
ONE Poly1305 tag per entire logical chunk - not per 64 KB block. Tag covers the complete ciphertext. Streaming-friendly. Nonce counter incremented BEFORE upload begins.
AES-256-GCM
Key wrapping, small structs
Per-file key wrapping, index entries, share packages. Full plaintext always in memory - GCM appropriate here.
BLAKE3 + file_size
Dedup key (pre-compression)
Hash computed on original file BEFORE zstd compression. Ensures same file deduplicates regardless of compression level or settings.
HMAC-SHA512
SQLite ledger chain
Every write chained to predecessor. Genesis block uses a defined initialization seed stored in keystore.json.
hmac.compare_digest
All secret comparisons
Constant-time comparison throughout codebase. Python == on bytes is NOT constant-time. All auth tag, hash, and passphrase comparisons use this.

4.3 Master Key Architecture
Key Derivation Chain:
passphrase
    → Argon2id (time=3, mem=64MB, parallelism=4)
    → Master Key (32 bytes)
    → HKDF-SHA512 with defined salt and info strings
        → Chunk Encryption Key (info: "sloth-chunk-enc-v1")
        → HMAC Key (info: "sloth-hmac-v1")
        → CLI Session Key (info: "sloth-cli-session-v1")
        → DB Snapshot Encryption Key (info: "sloth-db-snapshot-v1")

FIRST RUN (First-Launch UX Flow):
  Step 1 - User creates a passphrase (minimum entropy enforced, zxcvbn score ≥ 3).
  Step 2 - Master Key derived via Argon2id.
  Step 3 - Fresh ghostdrive.db created and encrypted.
  Step 4 - App immediately pushes DB snapshot to primary backend.
  Step 5 - App performs a test recovery: pulls the snapshot, decrypts it, verifies integrity.
  Step 6 - If verification passes, user is shown: "Your vault is backed up and recoverable. You're ready." If verification fails, user is warned and the issue must be resolved before proceeding.

NORMAL UNLOCK:
  Argon2id(passphrase) → Master Key (32 bytes) in ctypes buffer
  Passphrase zeroed from memory immediately (ctypes explicit zero)
  All workers receive memory-safe key reference ONLY

PASSPHRASE CHANGE:
  Unlock with current passphrase  →  Master Key derived
  Argon2id(new_passphrase)  →  new Master Key derived
  Re-encrypt the DB snapshot with the new Master Key.

RECOVERY (lost laptop / forgotten passphrase):
  Recovery is performed by importing a previously exported ghostdrive.db snapshot and entering the account passphrase.

4.4 Critical Cryptographic Rules
- Poly1305 authentication: ONE tag per logical chunk. The entire chunk ciphertext is authenticated as a single unit. Individual 64 KB blocks are NOT independently authenticated. The tag is appended after the last block and verified before any decrypted byte is returned to the application.
- Nonce counter: incremented BEFORE the chunk upload begins, not after it confirms. A wasted nonce from a failed upload is acceptable. A reused nonce from crash-before-increment is catastrophic under ChaCha20-Poly1305.
- Nonce counter increment and the operation it timestamps must be in the same SQLite transaction - atomic with the write they protect.
- ChaCha20-Poly1305 maximum message size is 2^38 - 64 bytes (~256 GB). No logical chunk approaches this. Documented for future developers.
- HKDF salt is fixed per installation, stored in keystore.json, and must be shared with the CLI and other devices for consistent subkey derivation.
- The HMAC ledger genesis block uses a defined initialization seed (stored in keystore.json), solving the chain verification edge case on a single-record database.

4.6 Key Material in Memory
Master Key and all derived keys held in ctypes buffers, explicitly zeroed after use. fsync() called after writing nonce counter, two-phase commit intent record, and keystore.json - ensuring these reach persistent storage before dependent operations begin. On Windows, VirtualLock() prevents paging of key material to pagefile.sys where privileges allow; documented as a known limitation where not available. App warns users that OS hibernation captures RAM.


5. Chunking Engine
5.1 Pipeline - Zero-Copy Streaming (Hard Constraint)
File ? OS file lock acquired ? zstd compress (skipped for pre-compressed formats) ? BLAKE3+size dedup check (on original, pre-compression) ? split into logical chunks ? nonce counter incremented (fsync) ? ChaCha20-Poly1305 stream via 64 KB generator ? Poly1305 tag appended after final block ? transmit as 50 MB sub-blocks ? distribute to backends.
64 KB generator streaming is a hard architectural constraint. No BytesIO buffers. No intermediate disk writes. The encryptor streams 64 KB blocks through update(), finalizes with a single Poly1305 tag, and yields directly to the network socket. asyncio.to_thread() wraps the encryptor.update() call to keep ChaCha20 CPU work off the main Qt thread. One persistent encryption thread per active upload stream - not one thread per block - to prevent thread pool exhaustion.
Streaming Pipeline (conceptual):
async def encrypted_chunk_stream(file_path, offset, size, key, nonce):
    # OS file lock held for duration of this call
    # nonce already incremented and fsynced before this is called
    encryptor = ChaCha20Poly1305(key)  # one instance per chunk
    async with aiofiles.open(file_path, "rb") as f:
        await f.seek(offset)
        bytes_read = 0
        while bytes_read < size:
            block = await f.read(min(65536, size - bytes_read))
            if not block: break
            ct_block = await asyncio.to_thread(encryptor.update, block)
            yield ct_block   # 64 KB ciphertext block -> socket
            bytes_read += len(block)
        tag = encryptor.finalize()  # ONE Poly1305 tag for entire chunk
        yield tag                   # appended after last block

# Assembly: concatenate all sub-blocks, verify tag LAST
# Never return any decrypted byte before tag verification passes

5.2 OS File Locking
The pre-hash double-read (BLAKE3 before upload, then re-read for encryption) is eliminated. A single streaming pass reads the file once. File integrity during upload is guaranteed by OS-level file locking:
- Linux/macOS: fcntl.flock(fd, LOCK_EX | LOCK_NB) at upload start
- Windows: msvcrt.locking() via a cross-platform abstraction wrapper
- Lock acquisition failure (permission error, read-only filesystem, another process holds lock): warn user, proceed without lock, flag file as uploaded-without-integrity-lock in index. Upload is not aborted.
- Lock held for entire upload duration. Released on completion, cancellation, or failure.

5.3 Thermal Throttling Backpressure
A Ryzen 5500U under sustained load will thermal throttle after 15-20 minutes, slowing encryption output. If encryption becomes slower than network send rate, upload stalls or times out. The pipeline implements backpressure: the network send rate is gated by encryption output, not assumed constant. If the encryption generator stalls, the upload coroutine waits rather than timing out.

Sub-block assembly rule: all sub-blocks must be present and concatenated before the Poly1305 tag (at the end of the final sub-block) is verified. Authentication is never attempted on a partial chunk.

5.5 Deduplication
BLAKE3 hash computed on the original file BEFORE zstd compression. This ensures the same file deduplicates regardless of compression level used on different devices or sessions. The composite key BLAKE3_hash + file_size is checked against the index. Match: soft-link entry, no re-upload. The byte-level verify pass is removed - SHA-256/BLAKE3 collision is not a practical concern.
Race condition fix: before starting an upload, a per-content-hash advisory lock is acquired in the database (exclusive transaction). A second concurrent upload of the same file waits, then deduplicates against the first upload's completed entry.

5.6 Two-Phase Commit and Quota Reservation
Before any chunk sub-block leaves the machine: (1) quota_reserved is decremented atomically in the backends table (SELECT + UPDATE in a single exclusive transaction - prevents two concurrent uploads double-spending the same quota); (2) a pending intent record is written to chunk_locations with status=pending and fsynced. Upload proceeds. On confirm: status updated to confirmed, quota_used incremented. On failure: status set to failed, quota_reserved restored.
On startup: pending records are scanned. The backend is queried to determine if the upload completed. Confirmed ? status updated. Not found ? status set to failed, quota_reserved restored.

5.7 Cancellation Flow
When a user cancels an in-progress upload: (1) the upload coroutine is cancelled via asyncio task cancellation; (2) the network stream is closed cleanly; (3) a backend delete() is attempted for any sub-blocks already confirmed; (4) the chunk_locations record is set to status=cancelled (distinct from failed); (5) quota_reserved is restored; (6) any in-progress healing tasks for this file's chunks are cancelled.

5.8 Reference Counting for Shared Chunks
Deduplication creates shared chunk ownership: multiple files reference the same chunk_id. A reference count is maintained per chunk (ref_count column in the chunks table). On file deletion (tombstone creation): ref_count is decremented for each of the file's chunks. Backend delete() is issued only when ref_count reaches zero. On tombstone vacuum: same check. A chunk is never deleted from a backend while ref_count > 0.

5.9 Edge Cases
- Empty files: stored as zero-sub-block manifest entry.
- Symlinks: followed with depth limit (max 10) to prevent infinite loops.
- Unicode filenames: explicit UTF-8 throughout via pathlib.
- File modified during upload: OS lock prevents modification. If lock unavailable and file changes detected post-upload (size mismatch): warn and re-upload.
- Last block padding: length stored in chunk header for unambiguous removal.
- zstd non-determinism: dedup hash computed pre-compression on original bytes. Compression level is a fixed constant (level 3) - never user-configurable for deduplication correctness.

6.3 Index Snapshot Cross-Backend Hash Verification
The index snapshot BLAKE3 hash must not be stored on the same backend as the snapshot file. An attacker controlling one backend could replace both the snapshot and its hash simultaneously. Fix: the snapshot hash is signed with the Master Key (HMAC-SHA512) and stored on a different backend from the snapshot file, or embedded in the Chunk 0 manifest of a sentinel file. On restore, the hash is retrieved from the alternate backend and verified before the snapshot is decrypted.

6.4 Routing Policy
Upload routing: N highest-priority healthy backends (N = tier redundancy level). Priority: health score, historical speed (from upload_history table), quota remaining, tier eligibility, and hot vs cold storage.
Download routing: fastest historically reliable backend first. Automatic fallback when a chunk is missing or fails authentication.

7.2 Chunk 0 Special Replication
Chunk 0 contains the complete file manifest (total chunk count, all BLAKE3 hashes, UUIDs, file metadata). If Chunk 0 is lost, the file is unrecoverable even if all other chunks are intact. Chunk 0 receives special treatment:
- Replicated to ALL active backends regardless of tier redundancy level.
- is_manifest flag in the chunks table identifies Chunk 0 records.
- Routing policy applies all-backends replication for is_manifest=true chunks.
- Chunk 0 integrity verified at every health check cycle, not on the leaky bucket schedule.
- Chunk 0 manifest re-uploaded when any subsequent chunk hash changes (format migration, re-encryption).

7.3 Corrupted Chunk Auto-Recovery
During file reassembly, if a chunk's Poly1305 authentication fails on one backend: (1) the app immediately tries the same chunk from the next-priority backend (automatic, no user action); (2) if all backends fail for the same chunk, the user is alerted with the specific chunk index and file name; (3) the chunk is flagged for emergency healing; (4) no partial decrypted data is ever returned to the application before full chunk authentication passes.

7.4 Alert Hierarchy
- 4+ backends healthy - silent.
- 3 backends healthy - passive status bar notice.
- 2 backends healthy - persistent banner every app open. Emergency Cross-Mirroring offered.
- 1 backend healthy - full-screen blocking modal. [Mirror Now] [Add Backend] only dismissible actions.
- 0 backends - read-only emergency mode. Thumbnails and index accessible locally.

7.5 Lazy Polling - No Startup Storm
On startup: ZERO network calls for chunk verification. Health states read from SQLite cache only. Background health daemon uses leaky bucket: randomised 1% daily chunk sample per backend. Full sweep: manual only. Prevents IP-level rate-limit bans from simultaneous health checks on launch.

7.6 Healing Trickle Queue - No Thundering Herd
Healing daemon: isolated low-priority background queue. Randomised exponential backoff. Pauses on foreground upload. Max 1 healing chunk per backend concurrently. Configurable healing rate (default: conservative). A 50 GB backend failure does not cascade into a DDoS against surviving backends.

7.7 Emergency Cross-Mirroring
At 2 active backends: streams chunks from surviving backends directly to a newly added backend. No local disk buffering. No requirement for local free space. Total storage exhaustion detection: when sum(quota_used) approaches sum(quota_limit) across all backends, a proactive alert recommends adding new backends or upgrading tiers before the crisis point.

7.8 DISPOSABLE Tier Cleanup
DISPOSABLE tier files deleted from the index have their backend chunks deleted immediately, not after a 30-day tombstone wait. DISPOSABLE data is explicitly marked as not worth preserving. Immediate deletion prevents quota consumption by abandoned experiments on quota-limited backends.

7.9 Headless CLI Companion
Single-file CLI that launches the local web server and exposes init/unlock, status, file listing, upload, download, delete, trash, share, backend diagnostics, integrity verification, and dependency checks. It uses the same service layer and database as the web UI; no session-key handoff is required.
Share operations return a URL that can be opened in the browser. All destructive operations require the local database to be unlocked first.

8.3 Lamport Clock Atomicity
logical_clock increment and the operation it timestamps are in the same SQLite transaction. Batch operations (move folder of 200 files) share the same logical_clock value with a secondary sequence number (batch_seq) within the batch. Merge rule: highest logical_clock wins for metadata conflicts. Equal clock: highest batch_seq wins. Clock value stored in index_snapshots manifest and validated on cold-start restore.

8.4 WAL Checkpoint Protocol
Before any index snapshot: PRAGMA wal_checkpoint(TRUNCATE) executed. WAL checkpoint and snapshot copy are logged to telemetry panel. The logical_clock increment and WAL checkpoint are in the same transaction for clock-sensitive operations.

8.5 Tombstone Vacuum Protocol
30-day TTL for CRITICAL and IMPORTANT tombstones. DISPOSABLE: immediate deletion. Nightly vacuum procedure: (1) UPDATE sensitive columns (name, path, MIME type, timestamps, thumbnail blob) with random bytes; (2) DELETE row; (3) purge corresponding FTS5 entries from ghostdrive_search.fts; (4) decrement ref_count for chunk references, issue backend delete() for zero-ref chunks; (5) PRAGMA secure_delete=ON + VACUUM; (6) record vacuum event in HMAC ledger. Limitation: pre-vacuum index snapshots on backends retain tombstone data.

8.6 Index Bootstrap - Cold Start Recovery
On fresh install: check all configured backends for index snapshot at deterministic path (derived from Master Key fingerprint via HKDF). Snapshot hash retrieved from a DIFFERENT backend than the snapshot file (cross-backend hash verification). HMAC-SHA512 signature verified against Master Key before decryption. If hash verification fails: snapshot rejected, try next backend. This prevents a compromised backend from serving a tampered snapshot.
During index bootstrap (may take minutes for large indexes): GUI shows skeleton loading state with progress indicator. Search disabled. All other operations (adding backends, viewing help) remain available.

8.7 integrity_log Pruning
integrity_log retains last 10 verification results per chunk_id. Older entries deleted automatically during nightly maintenance. The synced ghostdrive.db is bounded in size. Thumbnails contribute approximately 12 KB per file on average. At 10,000 files this is approximately 120 MB total - a one-time ceiling reached only when files stop being added, not an unbounded growth problem. Upload history and integrity_log are bounded by existing pruning mechanisms already defined in the spec. The only unbounded local data is the LRU block cache, which lives in ghostdrive_cache/ and is never synced.

8.8 Multi-Device Sync Protocol
After every write to ghostdrive.db, the application pushes an encrypted snapshot of the database to the primary backend at a deterministic path derived from a BLAKE3 hash of the Master Key fingerprint. The snapshot is encrypted with the same Master Key using AES-256-GCM.

On application launch, the app compares the local Lamport clock against the Lamport clock embedded in the remote snapshot. If the remote clock is higher, the app pulls the snapshot and performs a merge using the existing Lamport clock upsert logic. Conflicting records resolve by highest Lamport clock wins. This requires no central server - the primary backend acts as the sync relay.

On a new device, first-launch recovery flow is:
Step 1 - User selects "Restore existing vault."
Step 2 - User provides backend credentials (Telegram bot token, Discord bot token, NAS share, etc.).
Step 3 - App locates the DB snapshot on the primary backend automatically using the deterministic path.
Step 4 - User enters passphrase.
Step 5 - App decrypts and loads snapshot, verifies integrity, and is fully operational.

The app must prompt the user to verify this recovery flow works before allowing any uploads. This replaces the verification step that was previously required at first launch.

9.5 Clean Shutdown Sequence
On app close or SIGTERM (including OOM killer): (1) stop accepting new upload tasks; (2) complete current sub-block in progress; (3) drain upload queue (or cancel with cleanup flow); (4) flush in-memory SQLite commit batch; (5) WAL checkpoint; (6) zero key material from ctypes buffers; (7) close the SQLite connection; (8) exit. This sequence is registered as both a FastAPI shutdown hook and a Python signal handler (SIGTERM, SIGINT).

9.6 Exception Handling Philosophy
No silent exception swallowing anywhere in the upload/download/heal pipeline. Every exception must: (a) retry with backoff if transient network error; (b) mark chunk status as failed and restore quota_reserved if persistent; (c) escalate to telemetry panel as WARN or ERROR. A broad except Exception: pass is a banned pattern in all pipeline code. Code review must verify this before Month 2 ends.

9.7 Log Sanitization Rules
Raw API responses logged to telemetry panel must be sanitized before logging. Redacted fields: Authorization headers, Bearer tokens, signed URL query parameters, Telegram session tokens, account identifiers in error messages. A sanitize_for_log(response) function applies regex-based redaction before any API response reaches the log buffer. Applies to both in-memory telemetry and on-disk log files.

9.8 Additional UI Features
- Folder structure, tagging, and metadata editing.
- Dark and light mode.
- Storage analytics: per-backend, per-tier, per-type, per-month.
- GhostDrive Trash view: list, restore, and empty trash.
- Share links: create, list, revoke, and download.
- Per-file integrity verification action.


10. File Sharing
10.1 Share Links
A share link grants time-limited access to one file through the local server. Each link stores a token hash, optional PBKDF2-HMAC-SHA256 passcode verifier, expiry, download limit, and download count. The Master Key is never included in the link.

10.2 Access Control
Links may be protected by a passcode. Passcodes are derived with PBKDF2-HMAC-SHA256 (200,000 iterations) and a per-link salt. The server validates expiry, revocation, and download limit before returning plaintext.

10.3 Public Download
GET /s/{token} renders a passcode form when required; POST /s/{token} validates the passcode and streams the decrypted file as an attachment. Successful downloads increment the counter.

10.4 Revocation
Owners can list and revoke links. Revocation immediately invalidates the token. Already-downloaded copies cannot be recalled and the UI states this before sharing.

10.5 Scope
Share links expose individual files only. Contact exchange, QR codes, rendezvous delivery, folder sharing, and post-quantum recipient keys are not part of the current implementation.


11. Security Threat Model
What GhostDrive Protects Against
- Backend provider reading data: impossible - ChaCha20-Poly1305 before leaving machine.
- Backend account compromise: attacker sees authenticated encrypted blobs only.
- Third-party downloading chunks: cannot decrypt without Master Key.
- Chunk reordering/substitution: Poly1305 AAD binding detects.
- Chunk corruption/bitrot: Poly1305 tag and BLAKE3 hash detect.
- Index tampering: HMAC-SHA512 ledger chain detects.
- Passphrase brute force: Argon2id with calibrated parameters.
-- Timing attacks on secret comparisons: hmac.compare_digest throughout.
- Tampered index snapshot: cross-backend hash verification + HMAC signature.

What GhostDrive Does NOT Protect Against
- Malware on local machine with keylogger access to passphrase.
- Physical access to unlocked machine while app running.
- OS hibernation file capturing Master Key from RAM (VirtualLock where available; documented where not).
- Recovery is performed by importing a previously exported ghostdrive.db snapshot and entering the account passphrase.
- Pre-vacuum index snapshots on backends: tombstone data survives in pre-vacuum snapshots.
- India IT Act Section 69 lawful decryption orders: passphrase is the decryption key. No technical protection against lawful orders.
- GDPR right to erasure: encrypted ciphertext blobs may persist on backends after local deletion. Whether encrypted-but-unreadable satisfies GDPR Article 17 is a legal grey area. Documented.
- Network metadata leakage: upload timing and volume patterns are observable without decryption. Healing cascades visible as traffic spikes.
- iCloud/OneDrive sync of app data directory: if user stores app data in a synced folder, keystore.json metadata leaks to Apple/Microsoft.

User Responsibility Notice
Use of third-party services as storage backends may violate their Terms of Service. GhostDrive makes no warranty of service continuity. Users assume full responsibility for ToS compliance and applicable law in their jurisdiction. Export of strong encryption software may be subject to export control regulations.

15. Success Criteria
All of the following must be demonstrated before submission:
- Large file uploaded across three configured backends, retrieved with byte-perfect integrity.
- Killing one configured backend mid-download does not cause retrieval failure.
- Corrupted chunk (auth tag failure) on one backend: automatic fallback to another backend, no user action required.
- Losing configured redundancy triggers a persistent alert.
- Recovery is performed by importing a previously exported ghostdrive.db snapshot and entering the account passphrase.
- CRITICAL tier file verified on all configured backends.
- Startup with 1000+ files: zero network calls confirmed via telemetry panel.
- Discord backend mid-session: ephemeral URL refresh successful, no download failure.
- Two concurrent uploads of same file: deduplication lock prevents double-upload.
- Share link with passcode downloads the file and honors expiry, download limit, and revocation.
- Trash restore preserves metadata and chunk locations.
- Integrity verification detects a missing or corrupted chunk.
- Reed-Solomon 4+2 repair restores missing shards.
- hmac.compare_digest used for all secret comparisons: verified by code review.
- Exception handling audit: no silent except pass in any pipeline path.
